## Purpose

A native Android app + home-screen widget that reads/edits the user's Obsidian daily-note to-do list directly, bypassing the (slow) Obsidian app. Widget for glancing at today's checkboxes; an in-app screen for editing the full daily note.

## Constraints (decided, don't re-ask)

- **No Android Studio.** Build and deploy from the CLI only: `./gradlew assembleDebug` / `./gradlew installDebug`, `adb` to push to an already-installed Android VM/emulator.
- **No Tasker, no Syncthing.** The Obsidian vault reaches the phone via a Termux script that `git pull`s automatically into Android shared storage (`~/storage/shared/...`), which is what makes this app's SAF-based approach viable.
- **No backend/server.** Because the vault lands in *shared* storage (not Termux's private sandbox), the app reads/writes the files directly via SAF — no localhost server, no sync protocol of its own.

## Architecture

- **Kotlin + Gradle (Kotlin DSL)** — single app module, no Android Studio project files needed to build/run.
- **Two direct, independent SAF pickers — no vault root, no guessing.** "Choose daily folder" (`ACTION_OPEN_DOCUMENT_TREE`, `VaultPrefs.treeUri`) points straight at the daily-notes folder itself (e.g. `02 - daily`); "Choose daily template" (`ACTION_OPEN_DOCUMENT`, `VaultPrefs.templateUri`) points straight at the template file. Both persisted via `takePersistableUriPermission`. `DailyNote` treats `treeUri` as literally the daily folder — no subfolder/sibling search, since SAF can't walk up to a parent anyway. "Create today's note" copies the picked template if set, else starts blank.
- **Settings are a separate screen, not inline above the editor.** `MainActivity`'s `Scaffold`/`TopAppBar` toggles between `SettingsScreen` (the two pickers) and `EditorScreen` (note preview/edit) via a `showSettings` bool — a `⚙` action opens settings, `Done` closes it. Lands on settings first run (no daily folder picked yet); everyday use opens straight to the editor. The top bar title shows the open file's name (not a static "DailyObsi" label) once a note is loaded, and `Back to today`/`Edit`↔`Read` live in the top bar actions (left-to-right in that order) rather than a row above the note, so the note body gets the vertical space back.
- **Reading mode is the default, edit mode is opt-in.** `EditorScreen` renders `MarkdownView` (`Markdown.kt`) unless `editMode` is toggled via the top bar's `Edit`/`Read` action. `loadNote()` always resets `editMode = false`, so opening a note (today, or "yesterday" below) starts in reading mode.
- **Edit mode's checkbox lines and font size mirror reading mode.** `highlightMarkdownForEdit`'s checkbox branch swaps just the 1-char mark (`x`/` `) for a same-length checkbox glyph (`☑`/`☐`, colored/bold) instead of leaving raw `[x]`/`[ ]` in monospace — still literally editing the real `x`/space character underneath, only the display glyph changes (same trick as password masking). The `BasicTextField`'s base `textStyle` was bumped from `bodyMedium` (14sp, "way too small") to `bodyLarge` (16sp, reading mode's size) with `fontSize` dialed back slightly to 15sp since edit mode also carries visible raw syntax.
- **Edit mode is a borderless, fullscreen `BasicTextField` with no Save button.** No `OutlinedTextField` box/frame, no padding around it (`EditorScreen` zeroes the outer `Column`'s padding specifically when `editMode`) — the raw markdown gets the whole screen. There's no Save action at all: `DailyObsiApp` autosaves on a 10s `LaunchedEffect(editMode)` tick while editing, on `ON_STOP` (`LifecycleEventObserver`, e.g. backgrounding/killing the app mid-edit), and immediately whenever edit mode is exited — via the top bar's `Edit`/`Read` toggle *or* the system back button, both routed through one `exitEditMode()` that persists then flips `editMode = false`. Back is intercepted with `BackHandler(enabled = editMode)` so it exits to reading mode instead of leaving the screen/app while editing.
- **`Markdown.kt` is a pragmatic renderer, not full CommonMark** — scoped to exactly what `00 - todo/daily template.md` actually uses: `#`/`##`/... headers (vs. Obsidian `#tag` lines, which need the space-after-# distinction to tell apart; headers are collapsible in reading mode, see below), bold/italic/strikethrough/inline code, `==highlights==` and `<mark class="hltr-flashy-*">` HTML highlights (Highlightr plugin — color guessed from the class name), `[[wikilinks|alias]]` (styled only, not navigable — the rest of the vault isn't in the SAF grant), `![[embeds]]` (resolved to a real image via Coil + `DailyNote.findAttachment`'s bounded-depth SAF search when findable — usually *isn't*, since attachments live next to the vault root, outside the picked daily folder; falls back to a "not found" placeholder rather than failing silently), ordered/unordered/checkbox lists with indentation, blockquotes, horizontal rules, and fenced ` ```progressbar ` blocks. Progress-bar blocks with `kind: manual` + `button: true` (the medication/task counters) get real `−`/`+` controls that rewrite the block's `value:` line in place; `day-year`/`day-custom` kinds compute progress from dates instead and aren't interactive. Every interaction in reading mode (checkbox toggle, indent shift, reorder, progress +/-) routes through the same `persist()` in `DailyObsiApp` — writes the file and calls `TodoWidget().updateAll()`, so nothing needs an explicit save.
- **Checkbox rows: `▲`/`▼` (Material `KeyboardArrowUp`/`Down` icons) reorder the line, a horizontal swipe indents/outdents it.** `DailyNote.moveLine` swaps a line with its immediate neighbor for reordering tasks vertically, disabled at the file's first/last line. Indent/outdent (`DailyNote.shiftIndent`) moved off dedicated buttons onto a swipe gesture on the row itself, firing `onShiftIndent` once past a ~56dp threshold on release, not continuously per pixel. The gesture is hand-rolled (`awaitEachGesture`/`awaitFirstDown`, not `detectHorizontalDragGestures`) specifically to coexist with the enclosing `LazyColumn`'s vertical scroll: plain horizontal-only drag detection has no concept of "this gesture is actually a scroll" and steals any touch the moment its horizontal component crosses touch-slop, even on a mostly-vertical swipe. The fix waits for slop on *either* axis, then only locks into swipe handling (and starts calling `change.consume()`) if the horizontal delta clearly dominates the vertical one (1.5x); otherwise it bails without consuming so the list scroll gets the gesture instead.
- **Headers are color-coded by level** (`headerColorFor` in `Markdown.kt`, used in both reading and edit mode): h2 pink, h3 flamingo, h4 rosewater, h6 blue, h1/h5 left at the default text color — matching leftover AnuPpuccin `style-settings` config found in the vault (`.obsidian/plugins/obsidian-style-settings/data.json`), even though the *currently active* theme (`Velocity Custom`) doesn't itself use distinct header hues (its `--h1-color`..`--h6-color` are just low-saturation lightness steps of one base tone). Colors are the Catppuccin *Latte* hex values specifically, not Mocha — Mocha's pastels are too washed out against a light background and this app doesn't split header color by light/dark theme.
- **`EmbedImage` caches resolved `![[embed]]` URIs process-wide** (`attachmentUriCache` in `Markdown.kt`, keyed on `"dailyUri|name"`) — without it, every time a `LazyColumn` item holding an embed scrolled out of the viewport and back in, Compose disposed and recomposed it from scratch, re-running the bounded-depth SAF `findAttachment` DFS and re-fetching the image on every re-entry (visible as a "reload" flash). The cache survives across recompositions/scrolls for the life of the process; a stale-attachment edge case (a note's image swapped out on disk without an app restart) isn't handled, consistent with this app's existing bias toward simplicity here.
- **Headers are collapsible in reading mode.** Tapping a header (▼/▶ prefix) toggles a per-line `collapsedHeaders: SnapshotStateMap<Int, Boolean>` in `MarkdownView`, keyed on `viewingDate` (not `text`) so a checkbox toggle/indent/reorder elsewhere doesn't reset fold state — none of those change line count/order for existing headers. `MarkdownView` filters `blocks` down to `visibleBlocks` each recomposition: collapsing a header hides every block after it up to (not including) the next header whose level is `<=` its own, i.e. a sibling or ancestor closing the section; deeper headers inside a collapsed section stay hidden regardless of their own fold state.
- **Edit mode gets the same visual styling, via `VisualTransformation`, not a second renderer.** `highlightMarkdownForEdit`/`MarkdownVisualTransformation` re-style the raw text a TextField already holds — bold/italic/highlights/headers/etc. all render, but unlike reading mode's `appendMarkdownInline` (which *hides* delimiters like `**`), this variant keeps every character and only dims the markdown syntax around it, because `OffsetMapping.Identity` requires the transform never change the character count or cursor/selection desync. Interactive widgets (real checkboxes, progress +/-) can't exist here — a TextField can't embed composables mid-text — that's what reading mode is for.
- **Missing today's note → offers yesterday, not just "create".** If there's no file for today, `EditorScreen` checks whether yesterday's note exists (`DailyNote.findFile(..., date.minusDays(1))`) and if so offers both "Open yesterday's note" and "Create today's note" side by side, rather than forcing straight into a blank note. Viewing a non-today date shows a "Back to today" action in the top bar.
- **Launcher icon supports Android 13+ themed (monochrome) icons.** `mipmap-anydpi-v26/ic_launcher*.xml` add a `<monochrome>` layer pointing at the same flat white shape already used for `ic_launcher_foreground` (no separate asset needed since it has no baked-in color) — the system recolors it to match the wallpaper/Material You palette when the user has "Themed icons" on, on launchers that support it (stock Pixel does).
- **Jetpack Glance** (`androidx.glance`) — the home-screen widget. Extracts today's checkbox lines with a plain regex on `- [ ]` / `- [x]` (no markdown parser needed for this). Tapping a line toggles the checkbox in place in the underlying file. A manual "↻" refresh tap forces a re-read since `provideGlance` always reads the file fresh — closes the gap between Termux's `git pull` and the OS's own ~30min widget refresh tick (there's no true push/FileObserver refresh; SAF-backed shared-storage URIs don't reliably support that).
- **Jetpack Compose** — the in-app screen: a full-file multiline text editor over the daily note's raw markdown; save writes straight back to the same file via `DocumentFile`. `MainActivity.onCreate` calls `enableEdgeToEdge()` *and* the root `Surface` uses `.safeDrawingPadding()` — both are needed: edge-to-edge alone leaves the old opaque light-theme scrim behind the status/nav bars (looks like stray white bars), `enableEdgeToEdge()` makes them transparent/theme-matched instead. `res/values/themes.xml` + `res/values-night/themes.xml` split on `Theme.DeviceDefault(.Light).NoActionBar` for the window base (there's no framework "DayNight" style without AppCompat/Material Components, so the resource-qualifier split *is* the day/night switch). Theme color uses Material You dynamic color (`dynamicLightColorScheme`/`dynamicDarkColorScheme`) on API 31+, falling back to stock Material3 below that — confirmed against `../grid9`'s identical pattern. Note: dynamic color reflects the system's actual `theme_customization_overlay_packages` color source (e.g. `home_wallpaper`) — if that's wallpaper-derived rather than a manually-picked swatch, the app will correctly render whatever the wallpaper extracts to, not necessarily whatever's shown in a Settings color picker.

The git-pulled file in shared storage is the single source of truth; widget and editor both read/write it directly, no intermediate state.

## Local dev environment (this machine)

The Android SDK is split across two roots — both are needed, for different things:

- `/opt/android-sdk` — the default `$ANDROID_HOME`/`$ANDROID_SDK_ROOT`, has `cmdline-tools`, `sdkmanager`, `avdmanager`, `platform-tools/adb`. Use this for building (`./gradlew`) and `adb`. It does **not** have the emulator system image.
- `/home/ayaya/Android/Sdk-avd` — has the `emulator` binary and the actual system image (`system-images/android-35/google_apis/x86_64`). To launch the emulator, point env vars here instead:
  ```
  ANDROID_SDK_ROOT=/home/ayaya/Android/Sdk-avd \
  ANDROID_HOME=/home/ayaya/Android/Sdk-avd \
  ANDROID_AVD_HOME=/home/ayaya/.config/.android/avd \
  /home/ayaya/Android/Sdk-avd/emulator/emulator -avd <name>
  ```
  (`ANDROID_AVD_HOME` is required — the AVD configs live in `~/.config/.android/avd`, not the default `~/.android/avd`.)

Configured AVDs: `grid9test`, `recoral_test` (both android-35 google_apis x86_64).

`app/build.gradle.kts` pins `buildToolsVersion = "37.0.0"` deliberately — that's what's actually installed under `/opt/android-sdk/build-tools/`. AGP's default (34.0.0) isn't installed and there's no `licenses/` dir to auto-accept it from, so leaving it unpinned fails the build on a license-not-accepted error.

**`./run.sh`** does the whole cycle in one shot: boots `grid9test` if no device is attached (skips straight to build if one already is), `assembleDebug`, `adb install -r`, force-stop + relaunch. Use this instead of re-deriving the env-var dance above by hand.

## Signing

`release-keystore.jks` (PKCS12, alias `dailyobsi`, self-signed, 10000-day validity) + `keystore.properties` hold the release signing key. Both are gitignored — never commit them. `app/build.gradle.kts` reads `keystore.properties` at config time and wires a `release` `signingConfig` only if the file exists, so a checkout without it still builds (just unsigned/debug-signed release). PKCS12 keystores don't support distinct store/key passwords — `keytool` silently reuses the store password for the key, so `keystore.properties`' `storePassword` and `keyPassword` are intentionally identical.
