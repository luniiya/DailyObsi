# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

Building and running on-device (emulator). `./gradlew assembleDebug` and `assembleRelease` (signed) both succeed — see Local dev environment below for the env vars needed. MainActivity (folder + template pickers, editor), the Glance widget (checkbox list, tap-to-toggle, manual refresh), Material You dynamic color, and edge-to-edge inset handling are implemented.

## Purpose

A native Android app + home-screen widget that reads/edits the user's Obsidian daily-note to-do list directly, bypassing the (slow) Obsidian app. Widget for glancing at today's checkboxes; an in-app screen for editing the full daily note.

## Constraints (decided, don't re-ask)

- **No Android Studio.** Build and deploy from the CLI only: `./gradlew assembleDebug` / `./gradlew installDebug`, `adb` to push to an already-installed Android VM/emulator.
- **No Tasker, no Syncthing.** The Obsidian vault reaches the phone via a Termux script that `git pull`s automatically into Android shared storage (`~/storage/shared/...`), which is what makes this app's SAF-based approach viable.
- **No backend/server.** Because the vault lands in *shared* storage (not Termux's private sandbox), the app reads/writes the files directly via SAF — no localhost server, no sync protocol of its own.

## Architecture

- **Kotlin + Gradle (Kotlin DSL)** — single app module, no Android Studio project files needed to build/run.
- **`DailyNote.findFiles` looks up any number of filenames in *one* directory-listing query, instead of `DocumentFile.findFile` (one query per lookup, each internally `1 + N` Binder round-trips for an N-file folder).** `DocumentFile.findFile` lists the folder (1 query) then calls `.getName()` per child to compare against the target name — and `TreeDocumentFile.getName()` is its own separate `ContentResolver.query`, not a cached read off the listing (confirmed via the ANR postmortem below: the stack bottomed out there). With 512 files in the real daily folder, that's up to 513 round-trips per lookup, doubled at startup for the today+yesterday-fallback case — genuinely multi-second, not theoretical (measured, logged via `Log.d("DailyObsiPerf", ...)` in `loadNoteSuspend`). `findFiles` reads `DISPLAY_NAME` directly off the same cursor row `DocumentsContract.buildChildDocumentsUriUsingTree`'s listing already returns, for any number of target names in one query — `loadNoteSuspend` now looks up today's file and (when relevant) yesterday's fallback together, one query total regardless of folder size. Measured after the fix: 177ms end-to-end (query + actual file read) against that same 512-file folder, down from an unmeasured but clearly multi-second stall before.
- **All SAF I/O (`DailyNote.findFile`/`readText`/`writeText`/`createTodayFile`) runs on `Dispatchers.IO`, never directly on the main thread.** `DailyObsiApp.loadNoteSuspend` is the suspend function that actually does the work (`withContext(Dispatchers.IO) { ... }` around the SAF calls, then resumes on Main to touch Compose state); `loadNote(date)` is a thin non-suspend wrapper (`scope.launch { loadNoteSuspend(date) }`) kept around specifically so the existing plain `onClick = { loadNote(...) }` call sites didn't all need to become coroutine-launching lambdas themselves. `persist()` and `onCreateToday` follow the same pattern. This *was* a real ANR on a physical device (Pixel 8 Pro, "Input dispatching timed out... waited 5001ms"), not a theoretical concern — `onOpenYesterday`'s plain `DailyNote.findFile(...)` call blocked the main thread on a slow Binder round-trip to the SAF DocumentsProvider (ContentResolver.query, several layers down from `DocumentFile.findFile`) long enough to freeze input dispatch and get killed. SAF calls go through Binder IPC to a separate provider process — there's no guarantee they're fast, especially against a large/actively-synced daily folder, so none of them are safe to call synchronously from a click handler or `LaunchedEffect` body directly.
- **Two direct, independent SAF pickers — no vault root, no guessing.** "Choose daily folder" (`ACTION_OPEN_DOCUMENT_TREE`, `VaultPrefs.treeUri`) points straight at the daily-notes folder itself (e.g. `02 - daily`); "Choose daily template" (`ACTION_OPEN_DOCUMENT`, `VaultPrefs.templateUri`) points straight at the template file. Both persisted via `takePersistableUriPermission`. `DailyNote` treats `treeUri` as literally the daily folder — no subfolder/sibling search, since SAF can't walk up to a parent anyway. "Create today's note" copies the picked template if set, else starts blank.
- **Settings are a separate screen, not inline above the editor.** `MainActivity`'s `Scaffold`/`TopAppBar` toggles between `SettingsScreen` (the two pickers) and `EditorScreen` (note preview/edit) via a `showSettings` bool — a `⚙` action opens settings, `Done` closes it. Lands on settings first run (no daily folder picked yet); everyday use opens straight to the editor. The top bar title shows the open file's name (not a static "DailyObsi" label) once a note is loaded, and `Back to today`/`Edit`↔`Read` live in the top bar actions (left-to-right in that order) rather than a row above the note, so the note body gets the vertical space back.
- **The markdown code is split across three files by concern, not one 1000+-line `Markdown.kt`:** `MarkdownParsing.kt` (shared regexes/`Block`/`parseBlocks`/`headerBodyLineRange`/colors — no Compose UI, imported by both of the below), `MarkdownReading.kt` (the LazyColumn-based reading-mode renderer: `MarkdownView`/`MarkdownLine`/`EmbedImage`/`CodeBlock`/`ProgressBarBlock`), and `MarkdownEditing.kt` (the `TextFieldState`-based raw-markdown editor: `MarkdownTextField`/`highlightMarkdownForEdit`/the input & output transformations). Things previously `private` in the single file were widened to default (public) visibility only where a different file now needs them — everything still file-scoped where it was before stays `private`. References below to "`Markdown.kt`" from before the split mean whichever of these three actually holds that symbol now.
- **Reading mode is the default, edit mode is opt-in.** `EditorScreen` renders `MarkdownView` (`MarkdownReading.kt`) unless `editMode` is toggled via the top bar's `Edit`/`Read` action. `loadNote()` always resets `editMode = false`, so opening a note (today, or "yesterday" below) starts in reading mode.
- **`MarkdownTextField` (`MarkdownEditing.kt`) is the shared raw-markdown editor for both main edit mode and the section editor, built on the newer `TextFieldState`-based `BasicTextField`** (`androidx.compose.foundation.text.input`, stable since Compose Foundation 1.8.0 — `app/build.gradle.kts` bumped `compose-bom` from `2024.12.01` to `2025.09.00` specifically for this), not the classic `(String, (String)->Unit)`/`TextFieldValue` overload used everywhere else historically. Two things that classic API genuinely can't do drove the switch:
  - **Checkbox lines render a real overlaid `Checkbox`, pixel-matched to reading mode**, not a styled-text lookalike. `markdownOutputTransformation` hides (transparent, not deleted — still reserves layout space) each checkbox line's `"- [ ]"`/`"- [x]"` span via `OutputTransformation.addStyle`, then `MarkdownTextField` overlays a real `Checkbox(onCheckedChange = null)` — non-interactive by design, since "in edit mode I just want to write" was explicit; tapping it does nothing rather than fighting cursor placement — positioned with `TextLayoutResult.getBoundingBox` at `CheckboxOverlaySpec.anchorOffset` (the hidden span's start, *after* leading indentation, matching reading mode's checkbox position after the indent padding). When `onShiftIndent`/`onMoveLine` are supplied (main edit mode only — see below), the same overlay also gets the swipe gesture (`detectSwipeToIndent`, shared with reading mode's checkbox row) and `▲`/`▼` reorder icons pinned to the field's right edge, matching reading mode there too.
  - **The overlay stays correctly positioned while scrolling** via a `ScrollState` hoisted in `MarkdownTextField` and passed to *both* `BasicTextField`'s own `scrollState` param and the overlay's `Modifier.offset` math (`... - scrollState.value`) — the classic API never exposed its internal scroll offset, which is what made this actually infeasible there; researched via the `Hyphen` Compose Multiplatform markdown editor's real source (`ui/checkbox/InlineCheckbox.kt`, `ui/internal/InlineContentHost.kt`) to confirm this exact shared-`ScrollState` pattern before building it. This still means one continuous text field (free typing, normal Enter/Backspace/multi-line select) rather than per-line fields — the alternative (segmenting edit mode into per-line composables so reading mode's row could be reused wholesale) was considered and explicitly rejected in favor of this, to preserve continuous typing.
  - **`onShiftIndent`/`onMoveLine` are optional params — `MarkdownTextField` always reports line indices local to whatever `value` it was given, not the file.** Main edit mode's `value` *is* the full file, so its callbacks operate on `text` directly. The section editor's `value` is the extracted draft, so its callbacks operate on `sectionDraft` via the same `onDraftChanged` the text editing already uses — *not* on the file directly, which would go stale against the still-open draft until Save overwrites it.
  - **No floating "insert checkbox" button, no per-row ⇤⇥▲▼ buttons, no swipe gesture** — all three were tried and ripped back out, in that order. The FAB (bottom-right, above the keyboard) sat right where a thumb naturally rests while typing, so normal typing kept accidentally re-triggering it *between keystrokes*, visibly shredding whatever word was being typed into a run of single-character checkbox lines. Its replacement, per-row ⇤⇥▲▼ buttons pinned to each checkbox row's right edge, and before that a full-row swipe zone, both had the same underlying problem from a different angle: any hit-target positioned on top of the row ate taps meant to place a cursor in the todo text right next to it -- unlike reading mode's row (plain static `Text`, nothing underneath to conflict with), this row's text *is* the real editable field. None of these threw an exception -- all placement/hit-testing bugs, not logic bugs.
  - **What's there instead: a single floating bubble, not tied to any row's position, acting on whichever line the cursor currently sits on.** One small `Surface` (bottom-end, `Modifier.imePadding()`, deliberately compact — 18dp icons in 32dp touch targets, `LocalMinimumInteractiveComponentSize provides 0.dp`, not full 48dp Material defaults, so it reads as a minor utility rather than a dominant FAB) holds all four ⇤⇥▲▼ `IconButton`s. `cursorLineIndex` is derived by counting `\n` before `state.selection.start` in `state.text`, recomputed via `remember(state.text, state.selection)`. Since there's exactly one bubble at a fixed screen position instead of one overlay per checkbox line scattered through the document, there's nothing left sitting on top of the text to steal cursor-placement taps.
  - **Bug fixed (round 1): every bubble tap used to snap the view to the very end of the document.** `MarkdownTextField`'s resync effect originally called `setTextAndPlaceCursorAtEnd(value)` unconditionally whenever `value` changed for a reason other than the field's own typing — but *every* ⇤⇥▲▼ tap changes `value` exactly that way (`onShiftIndent`/`onMoveLine` call `persist()` in `DailyObsiApp` directly, bypassing `onValueChange` entirely), so each tap slammed the cursor to the document's end.
  - **Bug fixed (round 2): round 1's fix — preserving the cursor's raw character *offset* across the resync — was itself wrong for `onMoveLine`.** Swapping two same-length adjacent lines leaves that offset pointing at the same *screen position*, which after the swap shows the *other* line's content — so moving a line down left the cursor sitting on whatever text moved up into its old spot, not following the text it actually started on. `PendingCursorFollow` (a small sealed type, set by each bubble button right before it calls `onShiftIndent`/`onMoveLine`, consumed by the next resync) fixes this properly: `MovedLine(fromLine, toLine)` carries the cursor's line-relative offset over to the line its content actually relocated to; `ReindentedLine(lineIndex)` keeps the cursor on the same line but shifts its offset-within-line by however many characters actually got added/removed at that line's start. `resolveCursorFollow` computes the resulting absolute offset; with no pending op (autosave, switching notes/sections) it just falls back to clamping the raw offset, same as round 1. `Log.d("DailyObsiEdit", ...)` calls sit on the resync and each bubble button's `onClick` so this class of bug is checkable via logcat next time, not just re-diagnosed by reading code.
  - **Checkbox lines auto-continue on Enter too, via the same `listContinuationInputTransformation`** ordered lists use (renamed from `orderedListInputTransformation`) — pressing Enter at the end of `"- [ ] text"`/`"- [x] text"` inserts a fresh *unchecked* `"- [ ] "` on the new line regardless of whether the split-off item was checked; Enter on an empty item strips the marker instead (exits the list), same rule as ordered lists. This is what actually creates new checkbox lines now -- not a button.
  - **Ordered-list auto-continue on Enter is an `InputTransformation`**, not a hand-diffed `TextFieldValue` comparison: `changes.getRange(0)`/`getOriginalRange(0)` directly identify "exactly one `\n` inserted, nothing replaced" without manual substring diffing. Pressing Enter at the end of a `"1. text"` line inserts `"2. "` on the new line (incrementing per existing item); Enter on an *empty* `"N. "` item strips the marker instead of continuing forever (Obsidian/Notion-style list-exit).
  - **All markdown styling (bold/italic/highlights/headers/etc.) is preserved by replaying `highlightMarkdownForEdit`'s existing `AnnotatedString.spanStyles` onto the `OutputTransformation`'s `TextFieldBuffer` via `addStyle`** — that function itself didn't need to change (it's still length-preserving, so its offsets stay 1:1 valid), only the wrapper around it did.
  - `value`/`onValueChange` stay a plain `String` API for both call sites — `MarkdownTextField` manages a `TextFieldState` internally, resyncing via `LaunchedEffect(value)` (`resolveCursorFollow`-computed cursor position, see the two bubble-cursor bugs above — not `setTextAndPlaceCursorAtEnd`, that was the first bug) whenever `value` changes for a reason other than its own edit; its own edits round-trip back to an equal `value` via `snapshotFlow { state.text.toString() }`, so the resync never fights mid-keystroke.
- **Edit mode's font size matches reading mode.** The field's base `textStyle` was bumped from `bodyMedium` (14sp, "way too small") to `bodyLarge` (16sp, reading mode's size) with `fontSize` dialed back slightly to 15sp since edit mode also carries visible raw syntax.
- **Edit mode uses a monospace font** (`fontFamily = FontFamily.Monospace` on both `MarkdownTextField` call sites — main edit mode and the section editor), per explicit request ("jetbrain mono or something any mono font"). Android's built-in generic monospace family, not a bundled custom font file — no extra asset/res/font work needed, matches raw markdown editing conventions well enough.
- **The settings action in the top bar is a real Material icon (`Icons.Filled.Settings`), not a "⚙" text glyph** — reported as looking bad ("ascii thing... eww"). `material-icons-core` was already a dependency (used elsewhere for `Edit`/`KeyboardArrowUp`/`KeyboardArrowDown`), `Settings` is part of that core set too, no extended-icons dependency needed.
- **Edit mode is a borderless, fullscreen `BasicTextField` with no Save button.** No `OutlinedTextField` box/frame, no padding around it (`EditorScreen` zeroes the outer `Column`'s padding specifically when `editMode`) — the raw markdown gets the whole screen. There's no Save action at all: `DailyObsiApp` autosaves on a 10s `LaunchedEffect(editMode)` tick while editing, on `ON_STOP` (`LifecycleEventObserver`, e.g. backgrounding/killing the app mid-edit), and immediately whenever edit mode is exited — via the top bar's `Edit`/`Read` toggle *or* the system back button, both routed through one `exitEditMode()` that persists then flips `editMode = false`. Back is intercepted with `BackHandler(enabled = editMode)` so it exits to reading mode instead of leaving the screen/app while editing.
- **The renderer is pragmatic, not full CommonMark** — scoped to exactly what `00 - todo/daily template.md` actually uses: `#`/`##`/... headers (vs. Obsidian `#tag` lines, which need the space-after-# distinction to tell apart; headers are collapsible in reading mode, see below), bold/italic/strikethrough/inline code, `==highlights==` and `<mark class="hltr-flashy-*">` HTML highlights (Highlightr plugin — color guessed from the class name), `[[wikilinks|alias]]` (styled only, not navigable — the rest of the vault isn't in the SAF grant), `![[embeds]]` (resolved to a real image via Coil + `DailyNote.findAttachment`'s bounded-depth SAF search when findable — usually *isn't*, since attachments live next to the vault root, outside the picked daily folder; falls back to a "not found" placeholder rather than failing silently), ordered/unordered/checkbox lists with indentation, blockquotes, horizontal rules, and fenced ` ```progressbar ` blocks. Progress-bar blocks with `kind: manual` + `button: true` (the medication/task counters) get real `−`/`+` controls that rewrite the block's `value:` line in place; `day-year`/`day-custom` kinds compute progress from dates instead and aren't interactive. Every interaction in reading mode (checkbox toggle, indent shift, reorder, progress +/-) routes through the same `persist()` in `DailyObsiApp` — writes the file and calls `TodoWidget().updateAll()`, so nothing needs an explicit save.
- **Checkbox rows: `▲`/`▼` (Material `KeyboardArrowUp`/`Down` icons) reorder the line, a horizontal swipe indents/outdents it.** `DailyNote.moveLine` swaps a line with its immediate neighbor for reordering tasks vertically, disabled at the file's first/last line. Indent/outdent (`DailyNote.shiftIndent`) moved off dedicated buttons onto a swipe gesture on the row itself, firing `onShiftIndent` once past a ~56dp threshold on release, not continuously per pixel. The gesture is hand-rolled (`awaitEachGesture`/`awaitFirstDown`, not `detectHorizontalDragGestures`) specifically to coexist with the enclosing `LazyColumn`'s vertical scroll: plain horizontal-only drag detection has no concept of "this gesture is actually a scroll" and steals any touch the moment its horizontal component crosses touch-slop, even on a mostly-vertical swipe. The fix waits for slop on *either* axis, then only locks into swipe handling (and starts calling `change.consume()`) if the horizontal delta clearly dominates the vertical one (1.5x); otherwise it bails without consuming so the list scroll gets the gesture instead.
- **Headers are color-coded by level** (`headerColorFor` in `MarkdownParsing.kt`, used by both `MarkdownReading.kt` and `MarkdownEditing.kt`): h2 pink, h3 flamingo, h4 rosewater, h6 blue, h1/h5 left at the default text color — matching leftover AnuPpuccin `style-settings` config found in the vault (`.obsidian/plugins/obsidian-style-settings/data.json`), even though the *currently active* theme (`Velocity Custom`) doesn't itself use distinct header hues (its `--h1-color`..`--h6-color` are just low-saturation lightness steps of one base tone). Colors are the Catppuccin *Latte* hex values specifically, not Mocha — Mocha's pastels are too washed out against a light background and this app doesn't split header color by light/dark theme.
- **Link color (`[[wikilinks]]` and `[text](url)`, both reading and edit mode) follows the current Material You dynamic theme accent, not a hardcoded color.** Fixed a real reported bug (links rendering a fixed blue regardless of the system/theme accent, which on this device's wallpaper-derived palette is a completely different hue). `MarkdownParsing.kt` no longer has a `LINK_COLOR` constant at all — `appendMarkdownInline` (`MarkdownReading.kt`) and `appendEditableInline`/`highlightMarkdownForEdit` (`MarkdownEditing.kt`) all take a `linkColor: Color` param now instead, since neither is itself `@Composable` and can't read `MaterialTheme` directly; each threads it through every recursive call. Resolved once per composable call site — `MarkdownLine` resolves `MaterialTheme.colorScheme.primary` and passes it into every `parseInline` call; `MarkdownTextField` resolves it once and passes it to `markdownOutputTransformation(linkColor)`, which is now a function returning a fresh `OutputTransformation` (via `remember(linkColor) { ... }`) instead of a fixed top-level `val`, so the color updates correctly across theme changes. The Glance widget renderer (`GlanceMarkdown.kt`'s `GlanceInlineText`) has the same fix, using `GlanceTheme.colors.primary` — trivial there since it was already dynamic-color-backed.
- **`EmbedImage` (`MarkdownReading.kt`) caches resolved `![[embed]]` URIs process-wide** (`attachmentUriCache` in `MarkdownParsing.kt`, keyed on `"dailyUri|name"`) — without it, every time a `LazyColumn` item holding an embed scrolled out of the viewport and back in, Compose disposed and recomposed it from scratch, re-running the bounded-depth SAF `findAttachment` DFS and re-fetching the image on every re-entry (visible as a "reload" flash). The cache survives across recompositions/scrolls for the life of the process; a stale-attachment edge case (a note's image swapped out on disk without an app restart) isn't handled, consistent with this app's existing bias toward simplicity here.
- **Headers are collapsible in reading mode, no fold-arrow indicator.** Tapping the header text itself toggles a per-line `collapsedHeaders: SnapshotStateMap<Int, Boolean>` in `MarkdownView`, keyed on `viewingDate` (not `text`) so a checkbox toggle/indent/reorder elsewhere doesn't reset fold state — none of those change line count/order for existing headers. `MarkdownView` filters `blocks` down to `visibleBlocks` each recomposition: collapsing a header hides every block after it up to (not including) the next header whose level is `<=` its own, i.e. a sibling or ancestor closing the section; deeper headers inside a collapsed section stay hidden regardless of their own fold state.
- **Edit mode gets the same visual styling as reading mode, not a second renderer, via `highlightMarkdownForEdit` (length-preserving, unlike reading mode's `appendMarkdownInline` which *hides* delimiters like `**`).** Its output is consumed by `markdownOutputTransformation` (see `MarkdownTextField` above) rather than the classic `VisualTransformation` this used before switching APIs. Progress-bar `+`/`-` still can't exist inline in edit mode's raw text (only checkboxes get a real overlaid widget, via the mechanism above) — that's what reading mode is for.
- **Missing today's note → offers yesterday, not just "create".** If there's no file for today, `EditorScreen` checks whether yesterday's note exists (`DailyNote.findFile(..., date.minusDays(1))`) and if so offers both "Open yesterday's note" and "Create today's note" side by side, rather than forcing straight into a blank note. Viewing a non-today date shows a "Back to today" action in the top bar.
- **Launcher icon supports Android 13+ themed (monochrome) icons.** `mipmap-anydpi-v26/ic_launcher*.xml` add a `<monochrome>` layer pointing at the same flat white shape already used for `ic_launcher_foreground` (no separate asset needed since it has no baked-in color) — the system recolors it to match the wallpaper/Material You palette when the user has "Themed icons" on, on launchers that support it (stock Pixel does).
- **Jetpack Glance** (`androidx.glance`) — the home-screen widget. Extracts today's checkbox lines with a plain regex on `- [ ]` / `- [x]` (no markdown parser needed for this). Tapping a line toggles the checkbox in place in the underlying file. A manual "↻" refresh tap forces a re-read since `provideGlance` always reads the file fresh — closes the gap between Termux's `git pull` and the OS's own ~30min widget refresh tick (there's no true push/FileObserver refresh; SAF-backed shared-storage URIs don't reliably support that).
- **Navigation bar background is forced fully transparent**, not `enableEdgeToEdge()`'s own default. Its default already makes the *status* bar transparent, but the *navigation* bar defaults to `SystemBarStyle.auto(DefaultLightScrim, DefaultDarkScrim)` — a translucent scrim (existing for contrast on 3-button nav) that was visibly tinting content behind it. Fixed with `enableEdgeToEdge(navigationBarStyle = SystemBarStyle.auto(Color.TRANSPARENT, Color.TRANSPARENT))` so content shows straight through. Trade-off not relevant here but worth knowing: on API 28 and below this scrim also kept 3-button nav icons legible over arbitrary content — fine to drop given this app only targets/tests modern gesture-nav devices.
- **Reading mode's list actually draws behind the (now-transparent) nav bar; every other screen opts back into staying clear of it.** Making the nav bar transparent alone did nothing visible, because the content area never extended into that space to begin with — `MainActivity`'s outer `Box` reserved the full `safeDrawingPadding()` (all four sides), so nothing was ever drawn back there for the transparency to reveal. Fixed by only reserving `WindowInsets.safeDrawing.only(Top + Horizontal)` at that outer level (bottom inset dropped globally), then adding `Modifier.navigationBarsPadding()` back locally everywhere that isn't reading mode: `EditorScreen`'s `Column` when `editMode` or the empty (no-note) state, both `MarkdownTextField` call sites (main edit mode and the section editor), and `SettingsScreen`. Reading mode's `MarkdownView`/`MarkdownLine` needed no changes — it simply never had that padding added, so removing the global reservation immediately let it fill the extra space. This was an explicit, deliberate scoping request — "only in reading mode, not editing mode" — not a blanket edge-to-edge change. One follow-up bug this caused: scrolled all the way down, the last item ended up sitting *underneath* the nav bar rather than clear of it, since there was no further room to scroll into. Fixed with `LazyColumn`'s `contentPadding = PaddingValues(bottom = WindowInsets.navigationBars.asPaddingValues().calculateBottomPadding())` — a trailing spacer matching the actual nav bar height, so the true end of the note can always scroll clear of the bar.
- **Reading mode's `Column` and both `MarkdownTextField` call sites (main edit mode + section editor) all use zero bottom padding, only top/left/right.** A bottom margin on any of these stacks on top of the safe-area inset already reserved once (`MainActivity`'s outer `safeDrawingPadding()`), needlessly shrinking how far the list/field can actually use before its last line clears the gesture-nav area — this was a real, reported "big gap at the bottom" bug, not a hypothetical. Edit mode was already edge-to-edge on its outer `Column` for unrelated reasons (as much room as possible for raw text) but `MarkdownTextField`'s own modifier still separately added `vertical = 8.dp`, which needed the identical fix.
- **Jetpack Compose** — the in-app screen: a full-file multiline text editor over the daily note's raw markdown; save writes straight back to the same file via `DocumentFile`. `MainActivity.onCreate` calls `enableEdgeToEdge()` *and* wraps content in `Surface(Modifier.fillMaxSize())` → inner `Box(Modifier.safeDrawingPadding())` — the padding goes on the *inner* Box, not the Surface itself. Padding the Surface directly shrinks its own bounds inward by the inset, so its background color never reaches behind the status/nav bars at all, leaving a visible mismatched-color gap/seam right at the screen edge (most noticeable as a "border" above the gesture-nav pill); with the inner Box instead, the Surface's background fills the literal full screen and only the content is pushed clear of the system bars. `res/values/themes.xml` + `res/values-night/themes.xml` split on `Theme.DeviceDefault(.Light).NoActionBar` for the window base (there's no framework "DayNight" style without AppCompat/Material Components, so the resource-qualifier split *is* the day/night switch). Theme color uses Material You dynamic color (`dynamicLightColorScheme`/`dynamicDarkColorScheme`) on API 31+, falling back to stock Material3 below that — confirmed against `../grid9`'s identical pattern. Note: dynamic color reflects the system's actual `theme_customization_overlay_packages` color source (e.g. `home_wallpaper`) — if that's wallpaper-derived rather than a manually-picked swatch, the app will correctly render whatever the wallpaper extracts to, not necessarily whatever's shown in a Settings color picker.
- **Embedded images get rounded corners** (`Modifier.clip(RoundedCornerShape(12.dp))` in `EmbedImage`).
- **Section editor: a pencil icon next to each header opens a separate page to edit just that header's body**, not the header text and not the whole note. `headerBodyLineRange(text, headerLineIndex)` (`MarkdownParsing.kt`) computes the inclusive raw-line range of the body — same boundary rule as the collapse feature (up to, not including, the next header whose level is `<=` this one), walking `parseBlocks` rather than raw lines so a `#` inside a fenced code block is never mistaken for a heading. `DailyObsiApp.openSectionEditor` extracts that range into `sectionDraft` and sets `editingSectionLine`, which is a third top-level screen state alongside `showSettings`/the editor (checked first in both the `TopAppBar` and the `Scaffold` content `when`/`if` chain) — its own `SectionEditorScreen` is the same borderless fullscreen `MarkdownTextField` as main edit mode, scoped to the draft string, *with* `onShiftIndent`/`onMoveLine` wired too — but operating on `sectionDraft` via `onDraftChanged`, not on the file directly (see `MarkdownTextField`'s doc comment for why: its line indices are always local to whatever `value` it's given, and the file won't reflect the draft until Save). Save (`DailyNote.replaceLines`) or Cancel both close it back to the reading page; system back while it's open is wired to Cancel via `BackHandler(enabled = editingSectionLine != null)`. No autosave here (unlike main edit mode) since leaving the page always resolves one way or the other via the top bar actions.

The git-pulled file in shared storage is the single source of truth; widget and editor both read/write it directly, no intermediate state.

## Three-widget system (built, not yet placed/exercised on-device by a human)

All three widgets are coded, compile clean (`assembleDebug`), install clean, and produce no crash/exception in logcat on launch, and have since been placed and tapped through extensively on-device (see the checkbox/progress-refresh bug hunt below — that was found and fixed entirely through real on-device testing, not review). Build order was cheapest/lowest-risk first: **(1) edit-view shortcut → (2) single-heading → (3) full reading-view**, each phase informing the next.

**A fourth, pre-existing widget, `TodoWidget` ("Checklist" in the picker), was removed entirely** per explicit request ("remove the checklist widget completly it's useless and retarded" / "it was an old prototype") — it predated this three-widget system and was superseded by `HeadingWidget`/`ReadingViewWidget`, which cover the same checkbox-list use case plus more. Deleted `TodoWidget.kt`, `TodoWidgetReceiver.kt`, `todo_widget_info.xml`, its manifest `<receiver>` entry, and its `todo_widget_label`/`widget_description` string resources; `refreshAllWidgets()` (`WidgetKeys.kt`) no longer references it. Mentions of `TodoWidget` elsewhere in this doc below are left as-is where they're describing history (bugs found/fixed while it still existed) rather than current architecture.

- **Widget 1 — heading shortcut (`EditShortcutWidget.kt`).** Not a generic "open edit mode" button (that was the original, simpler plan) — corrected mid-build: **each placed instance is configured at placement time to point at one heading from today's note**, shows just that heading's title (no body content — that's Widget 2), and tapping it launches straight into the section editor scoped to that heading (`MainActivity.EXTRA_OPEN_SECTION_HEADING`), skipping both the reading-mode default and a generic full-note edit mode. `EXTRA_OPEN_EDIT_MODE` (the original shortcut-only extra) still exists and still works for a plain "jump to edit mode" launch, it's just not what this widget uses anymore.
- **Widget 2 — single heading (`HeadingWidget.kt`).** Renders one header's body (the same span `headerBodyLineRange` computes for the section editor) read-only-but-interactive — checkboxes and progress +/- are real taps, not just display. Configured the same way as Widget 1.
- **Widget 3 — full reading view (`ReadingViewWidget.kt`).** Same interactive renderer as Widget 2, scoped to every block in the file instead of one heading's body. No per-widget config screen — nothing to pick. A header row at the top opens the app to today's note for anything the compact renderer can't do (folding, the section editor, swipe-to-indent/reorder).
- **Per-widget heading selection is shared infrastructure, not duplicated per widget.** `HeadingPickerActivity.kt` is one `ACTION_APPWIDGET_CONFIGURE` activity used by *both* Widget 1 and Widget 2 (both are "pick one heading from today's note" widgets, just with different faces) — reads `AppWidgetManager.EXTRA_APPWIDGET_ID` from the launch intent, lists today's note's raw header lines (`HEADER.matches`), and on tap saves the **literal raw header line text** (e.g. `"## Health"`, not a line index) into that instance's `PreferencesGlanceStateDefinition` state via `updateAppWidgetState(context, PreferencesGlanceStateDefinition, glanceId) { ... }`, keyed by `SELECTED_HEADING_KEY` (`WidgetKeys.kt`). Storing the raw text instead of an index is deliberate: an index goes stale the instant the note is a fresh file next day, or an edit shifts lines above it; raw-text matching (`text.lines().indexOf(rawHeading)`) degrades gracefully to a "heading not found, place this widget again" message instead of silently pointing at the wrong section. Since a configure activity is declared, **the system does *not* automatically push an update to the newly-placed widget** (that's only true when there's no configure activity) — `HeadingPickerActivity` explicitly calls `refreshAllWidgets(context)` and `setResult(RESULT_OK, ...)` itself before finishing, matching that platform requirement.
- **`refreshAllWidgets(context)` (`WidgetKeys.kt`) replaces four separate `updateAll()` call sites with one.** Every widget reads the note fresh from disk on each `provideGlance`, so "something changed" always just means "recompose every placed instance of every widget class" — whether the change came from inside the app (`MainActivity.persist()`), a checkbox/progress tap on `TodoWidget`, or a checkbox/progress tap on `HeadingWidget`/`ReadingViewWidget`. Centralizing it here (rather than each call site separately calling `TodoWidget().updateAll(context)`, `HeadingWidget().updateAll(context)`, etc.) is what keeps adding a fourth widget later from requiring a hunt through every existing write path.
- **Bug found via real on-device testing, two rounds deep: a freshly-configured Widget 1/2 instance kept showing "Not configured" even though the save genuinely worked.** Diagnosed with `Log.d` on both sides of the round-trip (the state write, an immediate read-back in the same coroutine, and `provideGlance`'s own read) — the write and read-back both confirmed the correct heading was persisted, but `provideGlance` never ran a second time for that instance.
  - **Round 1 (real, but not the actual fix): enumeration-based refresh can miss a mid-configuration widget.** `refreshAllWidgets()`/`updateAll()` enumerates each widget class's *officially bound* instances via `GlanceAppWidgetManager.getGlanceIds()`, and a widget with a declared configure activity isn't "fully added" from `AppWidgetManager`'s own perspective until the configure activity returns `RESULT_OK` — so calling the enumeration-based refresh *before* that can silently skip exactly the instance being configured. Fixed in `HeadingPickerActivity` by additionally updating that specific `glanceId` directly (`EditShortcutWidget().update(context, glanceId)`, picked via `AppWidgetManager.getAppWidgetInfo(appWidgetId)?.provider?.className`) rather than relying solely on enumeration. This alone did not fix the bug — real on-device retest still showed "Not configured" with `Log.d` confirming `.update()` completed without error but `provideGlance` still never ran a second time.
  - **Round 2 (the actual root cause, found by reading Glance's real source — `AppWidgetSession.kt`, fetched from `dl.google.com/android/maven2` since it's not on Maven Central or resolvable via `cs.android.com`'s JS-rendered UI): `GlanceAppWidget.update()` does NOT re-invoke `provideGlance()` on an already-running session.** It only does that when no session exists yet (`startSession`); otherwise it calls `session.updateGlance()`, which just re-reads state through the widget's own `stateDefinition` property and pushes it into `LocalState` reactively — a plain `mutableStateOf(_, neverEqualPolicy())` that force-triggers recomposition on every call regardless of whether the value actually changed. Critically, `provideGlance`'s suspend *function body* — where the state read used to live, via a one-shot `getAppWidgetState()` call before `provideContent { }` — only ever runs **once** per session lifetime (confirmed from source: `remember { widget.runGlance(context, id) }` inside `AppWidgetSession`, and `runGlance` wraps a single `provideGlance()` call in a `channelFlow` that a normal implementation only emits into once via `provideContent`). Anything computed there before calling `provideContent` is permanently baked into every later recomposition, no matter how many times `.update()`/`.updateAll()` gets called afterward.
  - **The real fix: declare `override val stateDefinition = PreferencesGlanceStateDefinition` on every widget class, and read state reactively via `currentState<Preferences>()` *inside* `provideContent { }`, not via a one-shot suspend call before it.** Applied to `EditShortcutWidget` (trivial — the heading is the only thing it needs) and `HeadingWidget` (heading read reactively via `currentState()`, then the file read + block-slicing done as plain unconditional blocking calls directly in the composable body — same proven pattern `TodoWidget` already used — with only the genuinely-`suspend` embed-image resolution wrapped in `produceState(key1 = <the loaded blocks>)`). **`ReadingViewWidget` and `TodoWidget` needed the identical fix even though neither has any real per-instance config to read** — without *something* subscribing to `LocalState`/`currentState()` inside their composable, `updateGlance()`'s forced recomposition never reaches their content at all, so a checkbox tap or an in-app edit would silently stop updating the widget's face after its first render. Both now declare `stateDefinition` and call `currentState<Preferences>()` purely to hook the reactive trigger, discarding the value — `ReadingViewWidget`'s file read and `TodoWidget`'s existing checkbox-list read then run unconditionally on every recomposition that follows.
  - **Debugging this took `Log.d` on both sides of every hop (config-activity save, immediate read-back, provideGlance's own read) plus reading actual Glance source rather than guessing from API signatures alone** — the `.update()` semantics genuinely aren't discoverable from `javap`-level signatures (`suspend fun update(Context, GlanceId)`, no hint of the session-reuse branching inside). Per explicit instruction, logging stays in (`Log.d("DailyObsiWidget", ...)` at each hop) until every widget is confirmed working end-to-end on-device, not stripped once a fix merely looks plausible.
- **Widget picker labels: no "DailyObsi: " prefix.** Each widget's `<receiver>` needs its own `android:label` or the launcher's widget picker shows every one as just the `<application>` label ("DailyObsi", indistinguishable) — fixed via `todo_widget_label`/`edit_shortcut_widget_label`/`heading_widget_label`/`reading_view_widget_label` string resources. Initially included a "DailyObsi: " prefix on each, dropped per explicit feedback ("wow wait xml sucks omg... remove DailyObsi: at the beginning") — just "Checklist"/"Edit Heading"/"One Heading"/"Full Note" now.
- **Widget 1/2's icon is user-picked, not hardcoded.** `HeadingPickerActivity` has a second step after choosing the heading — a row of one-tap emoji suggestions (✏️📝✅📋🎯💊❤️📌⏰🔥) plus a free-text field (typing into it opens the system keyboard's own emoji key, the simplest way to get a real emoji picker without building one), stored alongside the heading via `SELECTED_EMOJI_KEY` (`WidgetKeys.kt`). `DEFAULT_WIDGET_EMOJI` ("✏️") is the fallback both for "Use default"/skip and for any instance configured before this feature existed (`prefs[SELECTED_EMOJI_KEY] ?: DEFAULT_WIDGET_EMOJI`, no migration needed). `EditShortcutWidget` shows it as its center icon (replacing the old hardcoded "✏️"); `HeadingWidget` shows it prefixed on its title line too, for consistency, since both share the same picker flow.
- **`logs.sh`** (repo root, alongside `run.sh`) — a filtered-logcat helper added specifically because manually retyping the same long `adb logcat -d | grep -iE "..."` command every debugging round trip got old. `./logs.sh` clears the buffer and tails live filtered to the app's own tags (`DailyObsiPerf`/`DailyObsiEdit`/`DailyObsiWidget`) plus the most relevant system components (`AppWidgetServiceImpl`, `GlanceAppWidget`, `AppWidgetHostView`); `./logs.sh dump` shows the current buffer without clearing/tailing; `./logs.sh crash` is a one-shot crash/exception-only scan (what the standing "check logcat after every install/launch" rule actually wants); `./logs.sh clear` just clears.
- **A second, parallel markdown renderer written specifically for Glance (`GlanceMarkdown.kt`)**, not a reuse of `MarkdownView`/`MarkdownReading.kt`. Glance compiles to `RemoteViews` under the hood and has its *own* separate composable set (`androidx.glance.Text`/`Column`/etc.) — none of the real `androidx.compose.material3`/`androidx.compose.foundation` composables `MarkdownView` uses are usable inside a widget, and this is a hard platform ceiling, not a Glance-specific limitation: widgets render inside the *launcher's* process via `RemoteViews`/`AppWidgetHost` (OS-level sandboxing, predates Glance entirely), so hand-writing a classic `AppWidgetProvider` + XML layout instead of using Glance would hit the exact same ceiling with much uglier code, not a higher one. `RemoteCompose` (Android 16's new binary widget-rendering engine, `androidx.compose.remote`) was investigated and found to not change this — still alpha (`1.0.0-alpha16`) against stable Glance (`1.2.0-rc01`) with zero integration yet, and its own modifier list has no blur and doesn't bridge to arbitrary app Compose code either.
  - **Real interactivity (checkboxes, progress +/-) was the deciding factor over pixel-identical rendering (Option B, explicitly confirmed over Option A's pixel-perfect-but-static bitmap render).** A bitmap has no click regions at all, and since these widgets are freely resizable, every resize would force a full re-render *and* recalculating any hardcoded tap-overlay positions to match.
  - **Rich inline text (bold+highlight+link mixed within one line) is a segmented-`Row`-of-`Text`s, via `parseInlineSegmentsForGlance` in `GlanceMarkdown.kt`** — a deliberate near-duplicate of `MarkdownReading.kt`'s `appendMarkdownInline` scanning logic (not a shared refactor, zero risk to the proven in-app renderer), emitting a flat `List<InlineRun>` instead of building an `AnnotatedString`. `GlanceInlineText` lays each run out as its own adjacent `Text`. Genuinely lost: a style spanning a mid-word line-wrap boundary. Not lost: swipe-to-indent/drag-to-reorder were never in scope for these widgets (`RemoteViews` click regions are simple taps only, no gesture detection).
  - **RemoteViews hard-caps a flat container (`Column`/`Row`) at 10 direct children — a real, currently-reproducing crash, not a theoretical one.** Found via the mandatory post-install logcat check: `TodoWidget`'s original plain `Column` of one `Row` per checkbox item (`items.forEach { ... }`, unbounded) threw `IllegalArgumentException: Column container cannot have more than 10 elements` the instant the real on-device daily note had more than 10 checkboxes, which it does. Fixed by switching it to `androidx.glance.appwidget.lazy.LazyColumn`/`items(...)`, which doesn't inflate every child into one flat container up front. `HeadingWidget`/`ReadingViewWidget` were designed around this from the start (each block renders inside its own `LazyColumn` item's single-child `Column`, never a flat list of N blocks in one container) but `GlanceInlineText`'s Row-of-inline-runs had the identical latent risk for a line with many style transitions — given a defensive cap (first 9 runs kept styled, any remainder collapsed into one final plain-text run) rather than risking the same crash on a pathological line.
  - **Checkboxes render via `androidx.glance.appwidget.CheckBox` (a real RemoteViews compound button), not the original "☑"/"☐" unicode-glyph `Text`.** The glyph version was reported as looking bad on-device — font rendering of those specific unicode characters varies a lot by system font/launcher and never actually looked like a real checkbox. Found Glance ships an actual native `CheckBox` composable by reading its source (`CheckBox.kt`) — `checked`/`onCheckedChange: Action?`/`colors: CheckBoxColors` (via `CheckboxDefaults.colors(checkedColor, uncheckedColor)`, tinted from `GlanceTheme.colors.primary`/`.outline` for dynamic-theme consistency).
  - **Checkbox tap handling took three rounds to get right, each disproven by the next round's logcat evidence rather than by reasoning about it.**
    - **Round 1: `onCheckedChange = null`, Row-only clickable (the original design).** Tapping the row mostly did nothing — across many taps, only ONE `GlanceCheckboxToggleAction.FIRED` ever showed up, matching a tap that happened to land on the checkbox glyph. Read as "the CompoundButton's own view bounds eat the touch before the Row's clickable sees it."
    - **Round 2: gave the `CheckBox` the same action too (matching in-app `MarkdownReading.kt`'s `Checkbox`+`Row` double-handler pattern), kept the Row's clickable.** Worse, not better: fuller logcat showed a single tap firing TWICE for the same line -- one `FIRED` with no extras (the Row), a second ~700ms later carrying `android.widget.extra.CHECKED` (the CheckBox's own native click semantics) -- toggling the line and then immediately toggling it back. This is "fires once in a blue moon" from the user's side, and the two independent, uncoordinated `onAction` calls each doing their own read-modify-write on the same file is also a genuine race (see `noteWriteMutex` below) that can lose a write outright, matching a separately reported "tick it and the line disappears."
    - **Round 3 (current): single handler only -- Row's `.clickable(...)`, `CheckBox`'s `onCheckedChange = null`.** Round 1's "only the glyph works" finding was thin (one data point across a whole test session) next to round 2's much richer, clearly-explained double-fire evidence: went back to the simpler design rather than trying to reconcile both partial pictures.
  - **`noteWriteMutex` (`WidgetKeys.kt`) serializes every widget-triggered read-modify-write of the note file** (`GlanceCheckboxToggleAction`, `GlanceProgressDeltaAction`, `TodoWidget`'s `ToggleTodoAction`) -- not just a fix for round 2's double-fire above, but a real general gap: any two of these `ActionCallback`s running close enough together (rapid taps across different lines, not just the same one) can interleave their independent `readText` → compute → `writeText` sequences, and the second call's read can miss the first call's not-yet-written change, silently losing it when the second call's own write lands. `withLock { }` around each action's full read-modify-write forces them to run one at a time.
  - **Images**: `resolveEmbedImagesForGlance` in `GlanceMarkdown.kt` — manual bitmap loading via the same `DailyNote.findAttachment` SAF lookup the app already uses, decoded on `Dispatchers.IO` inside `provideGlance` (before `provideContent` — Glance composables aren't `suspend`, so this can't happen reactively the way `EmbedImage`'s Coil `AsyncImage` does in-app), passed in as a pre-resolved `Map<String, ImageProvider>`.
  - **Embed sizing took two attempts.** First: a fixed `.height(140.dp)` + `ContentScale.Fit` letterboxed any image whose aspect ratio didn't match (reported: "whole ocean around images" — big empty margins around a tiny picture); `ContentScale.Crop` filled the box but visibly zoomed into/cropped the image (equally unacceptable — "we cant have images zoomed in that much", "they should always fit"). Second attempt manually computed a matching box height from `LocalSize.current` and the decoded bitmap's real aspect ratio — still came out small and centered, wrong. **Root cause found by reading Glance's actual translation code (`ImageTranslator.kt`, not guessed):** the real native-ImageView mechanism for "auto-size to the image's own aspect ratio" is `adjustViewBounds`, and Glance only enables it when `contentScale == Fit` **and** at least one dimension's modifier is `Wrap` — a fixed `.height(x)` (Fixed, not Wrap) meant it was never enabled regardless of how carefully that height was computed. Final fix: `.fillMaxWidth().wrapContentHeight()` with `ContentScale.Fit` — lets the real native view size itself from the actual decoded image, no manual math needed at all.
  - **No rounded corners on embeds.** Tried `.cornerRadius(12.dp)` (matching `EmbedImage`'s `RoundedCornerShape(12.dp)`/`.clip()` in-app), explicitly reported as looking bad on real widget rendering and dropped — plain rectangular corners only.
  - **Rapid consecutive checkbox taps visibly lag before the widget face catches up — confirmed, via full end-to-end logcat tracing across dozens of taps, to be RemoteViews/AppWidgetManager update coalescing under rapid successive pushes to the same widget instance, not a data-integrity bug.** Every single tap traced end-to-end (`FIRED` → before/after file content → write) fires exactly once and writes correctly, every time — cross-checked directly against the in-app reading view (source of truth) after a burst of rapid taps and found to match exactly once tapping paused. An isolated tap with a beat before the next one recomposes promptly; several taps within about a second of each other visibly lag before the widget repaints, then catches up. This matches a known Android platform characteristic (`AppWidgetManager.updateAppWidget()` pushes aren't instant and can be rate-limited/coalesced under rapid repeated calls to one widget) rather than anything fixable in this app's own code.
  - **A `pm clear dev.ayaya.dailyobsi` was run mid-debugging to test a (wrong) theory that Glance's internal receiver→provider mapping cache was stale** (`GlanceAppWidgetManager.getGlanceIds()` was observed returning an empty list for `TodoWidget`/`HeadingWidget`). This wiped the user's picked daily folder and all placed widgets' saved configuration without asking first — a real process mistake, not just a dead end. The empty lists turned out to be **correct, not stale**: the user simply had zero `TodoWidget`/`HeadingWidget` instances placed at the time, so an empty enumeration was the right answer, not a bug. Lesson: a destructive diagnostic action (clearing app data) needs confirmation first, even mid-investigation under time pressure — "let me test a theory" doesn't justify skipping that.
  - **The actual root cause of "checkbox ticks stopped showing up," found by tracing full before/after file content across several taps, not just tap events:** three checkboxes tapped within a few seconds each wrote correctly (confirmed line-by-line via `Log.d`), but a *later* render still showed the pre-toggle state for all three — stale data silently overwriting fresh data. `refreshAllWidgets()`/`.update()` only *enqueues* a recompose request on Glance's own session worker; it does not wait for the actual recompose + file re-read + RemoteViews push to finish (that happens asynchronously, decoupled from when `refreshAllWidgets()` returns). With several writes firing in quick succession, an older in-flight recompose — one that started its own file read *before* a later tap's write landed — can finish executing *after* a newer one already pushed fresher content, overwriting it. There's no public Glance API to wait for a session's pending recompose to actually land.
    - **First mitigation attempt: hold `refreshAllWidgets()` plus a fixed 350ms settle delay inside `noteWriteMutex`'s lock, per tap.** Wrong, and confirmed *worse* by the next real-device round: since every tap's `ActionCallback` now blocked for the full delay before returning, rapid-tapping a progress-bar +/- ("pressing plus 200 times and it still shows 0/4") made the widget feel completely dead, not just laggy -- each tap could only start once the previous one's artificial wait had fully elapsed.
    - **Actual fix: `requestWidgetRefresh(context)` (`WidgetKeys.kt`), a debounced trigger, replaces every direct `refreshAllWidgets()` call from a widget action or `MainActivity.persist()`.** The bug was never that `refreshAllWidgets()` needed to be slower -- it was calling it once per tap at all, letting independent recompose requests race each other. A `MutableSharedFlow<Context>` + `.debounce(200)` collapses a whole burst of taps into exactly ONE trailing `refreshAllWidgets()` call, fired 200ms after the *last* request in the burst -- which always reads the file's true final state at that point, since the write itself (still immediate, still mutex-protected, still un-delayed) has long since landed by then. Individual taps stay instant (the mutex now only guards the write, not the refresh); the widget catches up automatically shortly after the user actually stops tapping instead of visibly fighting itself mid-burst. The debounce collector is a single process-lifetime coroutine (`refreshScope`, a top-level `CoroutineScope(SupervisorJob() + Dispatchers.Default)`), started lazily on first reference to anything in `WidgetKeys.kt`, not per-call.
  - **Round G: tried content-derived `LazyColumn` `itemId`s** (`(i.toLong() shl 20) xor (block.hashCode().toLong() and 0xFFFFF)` in `ReadingViewWidget.kt`/`HeadingWidget.kt`, replacing Glance's default position-only id) on the theory that RemoteViews list items specifically weren't being re-bound on content-only changes. Installed and retested — the very next round of screenshots looked *worse*, not better: widget vs. in-app mismatched on almost every line, including one item checked in the widget but unchecked in-app (the *reverse* direction of "widget is behind"). That reversed mismatch was the tell that this whole hunt had been chasing the wrong culprit.
  - **The actual root cause (Round H, found by re-examining `MainActivity` itself instead of Glance internals): the in-app reading view used throughout this entire bug hunt as "ground truth" was itself stale.** `MainActivity`'s `text` (the note content backing the in-app reading/edit view) is loaded exactly once per note, via `LaunchedEffect(dailyUri)` on cold start / folder pick — nothing ever re-read it after that, including on resume. The widgets write straight to the file on disk and always read it fresh on every `provideGlance`, so they were correct the whole time; but backgrounding the app to tap a widget, then foregrounding it again to screenshot the "correct" in-app state for comparison, showed whatever `text` happened to be *before* backgrounding — not the current file. This explains every previously-confusing symptom at once: mismatches in *either* direction (depends only on which side, widget or stale in-memory app state, last touched a given line), mismatches that looked like "reverting to older state" (the in-app screenshot was simply from further in the past, the longer a test session ran without an app restart), and why Round G's fix looked like it made things worse (more taps had accumulated since the app's one-time load by the time that round's screenshots were taken, not because the fix itself regressed anything).
  - **The fix: reload the note from disk on `ON_START`,** in the same `LifecycleEventObserver` in `MainActivity` that already handles `ON_STOP` autosave (`DisposableEffect(lifecycleOwner)`). `loadNote(viewingDate)` fires whenever the activity comes back to the foreground, skipped only while `editMode` or the section editor is open (`editingSectionLine != null`) so a resume never clobbers in-progress unsaved typing — both of those already have their own save/exit paths that don't need this. This makes the in-app view a trustworthy comparison point again: after this fix, foregrounding the app always shows the true current file, including any widget-driven writes made while it was backgrounded. Verified via `./logs.sh crash` after install — clean, no `dailyobsi` exceptions. The content-derived `itemId` change from Round G was left in place (harmless — it just makes list items rebind more eagerly, never less correctly) rather than reverted, since it wasn't shown to be the actual cause of anything.
  - **Bug found via real on-device testing: a widget with an embedded image stopped updating after a few resizes.** Real crash in logcat, not a resize-handling bug per se: `IllegalArgumentException: RemoteViews for widget update exceeds maximum bitmap memory usage (used: 46485312, max: 15552000)`. `decodeSampledBitmap` (`GlanceMarkdown.kt`) was decoding embeds at native resolution (`BitmapFactory.decodeStream` with no options) — a normal phone photo (e.g. 4000×3000) decodes to ~48MB as ARGB_8888, blowing straight through RemoteViews' ~15MB per-update bitmap budget on its own; it only surfaced after a few resizes specifically because `SizeMode.Exact` recomposes (and thus re-decodes) on every size change, each attempt independently over budget. Fixed with the standard two-pass Android downsample: decode bounds only first (`inJustDecodeBounds`, no pixel allocation) to compute a power-of-two `inSampleSize`, then decode for real capped to ~600px on the long side — these widgets never display an embed taller than ~140dp anyway, so anything past a few hundred px was wasted memory the budget couldn't afford regardless.
- **"Frosted glass" and plain see-through transparency were both requested, then explicitly dropped as unnecessary** ("useless tbh") once the constraints were explained: true frosted glass (blurring the wallpaper behind the widget) genuinely isn't achievable for a home-screen widget on any current or alpha API — `RemoteViews` has no blur/compositing primitive an app can invoke itself, confirmed to persist even in `RemoteCompose`'s alpha modifier list.
- **The widget background must be opaque, not a faint alpha tint — confirmed by a real complaint ("the background is transparent while it shouldn't be") against the first cut's `Color(0x1F6750A4)`.** Fixed by wrapping each widget's content in `GlanceTheme(colors = androidx.glance.material3.ColorProviders(light = ..., dark = ...))` (both args resolved from `dynamicLightColorScheme(context)`/`dynamicDarkColorScheme(context)`, API<31-guarded to plain `lightColorScheme()`/`darkColorScheme()`, mirroring `MainActivity`'s own dynamic-color logic exactly) and setting the background to `GlanceTheme.colors.surface` — opaque by construction. Explicitly *not* `GlanceTheme`'s own no-arg default, which resolves to the library-internal (`@RestrictTo(LIBRARY_GROUP)`, unusable from app code, confirmed via decompiled source) `DynamicThemeColorProviders` — the two-`ColorScheme`-argument `ColorProviders(light, dark)` overload is what bakes in day/night switching itself from app-resolved colors, the documented/supported path.
- **All three widgets are freely resizable, no min/max beyond the platform's own floor** — `SizeMode.Exact` (reads the actual current widget size continuously via `LocalSize.current`) rather than `SizeMode.Responsive`/`SizeMode.Single`. Each `*_widget_info.xml` sets `minWidth`/`minHeight="40dp"` (platform floor) and omits `maxResizeWidth`/`maxResizeHeight` entirely.
- **API surface confirmed against decompiled real androidx source** (`javap` against the actual resolved `glance-*-1.1.1` jars in the Gradle cache, not guessed): `GlanceAppWidgetManager.getGlanceIdBy(Int)`, `getAppWidgetState`/`updateAppWidgetState(Context, GlanceStateDefinition<T>, GlanceId, ...)`, `androidx.glance.material3.ColorProviders(ColorScheme, ColorScheme)`, `GlanceModifier.cornerRadius(Dp)`/`.background(ColorProvider)`, `androidx.glance.appwidget.lazy.LazyColumn`/`items`, `androidx.glance.appwidget.LinearProgressIndicator`, `androidx.glance.Image`/`ImageProvider`/`ContentScale`. `defaultWeight()` turned out to be a `RowScope`/`ColumnScope` *member* extension, not a top-level import — caught by a real compile error, not caught in advance.

`app/build.gradle.kts` pins `buildToolsVersion = "37.0.0"` deliberately — that's what's actually installed under `/opt/android-sdk/build-tools/`. AGP's default (34.0.0) isn't installed and there's no `licenses/` dir to auto-accept it from, so leaving it unpinned fails the build on a license-not-accepted error.

**`./run.sh`** does the whole cycle in one shot: boots `grid9test` if no device is attached (skips straight to build if one already is), `assembleDebug`, `adb install -r`, force-stop + relaunch. Use this instead of re-deriving the env-var dance above by hand.

## Signing

`release-keystore.jks` (PKCS12, alias `dailyobsi`, self-signed, 10000-day validity) + `keystore.properties` hold the release signing key. Both are gitignored — never commit them. `app/build.gradle.kts` reads `keystore.properties` at config time and wires a `release` `signingConfig` only if the file exists, so a checkout without it still builds (just unsigned/debug-signed release). PKCS12 keystores don't support distinct store/key passwords — `keytool` silently reuses the store password for the key, so `keystore.properties`' `storePassword` and `keyPassword` are intentionally identical.

`assembleRelease` needs `lint { checkReleaseBuilds = false; abortOnError = false }` in `app/build.gradle.kts` — without it, AGP's default "lint vital" pass on the release build type hard-crashes (`NonNullableMutableLiveDataDetector`, a real AGP-8.7.3-vs-newer-Kotlin-analysis-API incompatibility, not a lint warning in this app's own code) and `assembleRelease` fails outright. This had never actually been exercised before setting up the GitHub Actions release workflow below — `run.sh`/local dev only ever ran `assembleDebug` — so it went unnoticed until then. Verified fixed via a `clean assembleRelease` (all tasks re-run, not a stale UP-TO-DATE result) and `apksigner verify --print-certs` on the resulting APK, confirming it's actually signed with the `dailyobsi` cert, not just "the build didn't error."

**`.github/workflows/release.yml`** builds a signed release APK on pushing a `v*` tag (or manually via the Actions tab's "Run workflow") and attaches it to a GitHub Release. Reconstructs `keystore.properties` + `release-keystore.jks` at build time from three repo secrets (`RELEASE_KEYSTORE_BASE64` — `base64 -w0 release-keystore.jks`, `RELEASE_KEYSTORE_PASSWORD`, `RELEASE_KEY_ALIAS` — `dailyobsi`) rather than committing them; without those secrets set the workflow still runs and produces an unsigned APK (with a warning), so the build itself is verifiable before signing is wired up.

## Testing

**Unit tests: `./test.sh`** (or `./test.sh ProgressBar` to filter by class name) — plain JVM tests under `app/src/test/java/dev/ayaya/dailyobsi/`, mirroring the main source folders, no emulator needed. Run it before every install. Feature logic is deliberately kept in pure functions so it's testable there, not buried in composables: note rewrites (`DailyNote.toggleCheckbox`/`shiftIndent`/`moveLine`/`replaceLines`), `parseBlocks`/`headerBodyLineRange`, `ProgressBar.kt` (`parseProgressBar`/`progressValueLine`, shared by the app reader *and* the widgets), edit mode's `listEnterFor`/`checkboxOverlaySpecs`/`horizontalRuleRanges`/`resolveCursorFollow` (`internal` for tests), `restoredSection` (which tab reopens), `bottomBarTabWidth`, and the widget's `parseInlineSegmentsForGlance`. When adding a feature, put its logic in a function like these and add a test.

**On-device testing is the user's job, not Claude's.** After a change: build, install, `./logs.sh crash`, then stop — never drive the emulator with `adb shell input`, since the user tests on it at the same time.

Installed and running on the `grid9test` AVD: a full copy of `~/obsidian/main` was `adb push`ed to `/sdcard/obsidian` on the emulator (not a symlink/sync -- a one-time snapshot copy, so it goes stale; re-push if the on-device vault needs to reflect later edits made on the dev machine), and `dev.ayaya.dailyobsi` is installed via `adb install -r`. When picking a folder in the app on this AVD, point it at `obsidian/main` under Internal storage.

**Check logcat after every install/launch, not just when something visibly breaks.** `adb logcat -c` right before `./run.sh` (or right after), then `adb logcat -d | grep -iE "dailyobsi.*(fatal|exception|error)"` once the app's up — a clean run should show nothing. Silent logic bugs (bad state, wrong output) won't throw, so this only catches crashes/exceptions, but it's a cheap check worth doing every time regardless, not just when chasing a specific crash.

## Vault layout (source of truth, external to this repo)

The Obsidian vault lives at `~/obsidian/main/` on the dev machine and is mirrored to the phone by Termux. Relevant folders: `00 - todo/` (daily-note template), `02 - daily/` (the actual daily notes this app targets).
