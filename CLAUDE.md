## Status

Building and running on-device (emulator). `./gradlew assembleDebug` and `assembleRelease` (signed) both succeed — see Local dev environment below for the env vars needed. MainActivity (folder + template pickers, editor), the Glance widget (checkbox list, tap-to-toggle, manual refresh), Material You dynamic color, and edge-to-edge inset handling are implemented.

## Purpose

A native Android app + home-screen widget that reads/edits the user's Obsidian daily-note to-do list directly, bypassing the (slow) Obsidian app. Widget for glancing at today's checkboxes; an in-app screen for editing the full daily note.

## Constraints (decided, don't re-ask)

- **No Android Studio.** Build and deploy from the CLI only: `./gradlew assembleDebug` / `./gradlew installDebug`, `adb` to push to an already-installed Android VM/emulator.
- **No Tasker, no Syncthing.** The Obsidian vault reaches the phone via a Termux script that `git pull`s automatically into Android shared storage (`~/storage/shared/...`), which is what makes this app's SAF-based approach viable.
- **No backend/server.** Because the vault lands in *shared* storage (not Termux's private sandbox), the app reads/writes the files directly via SAF — no localhost server, no sync protocol of its own.

## Architecture

- **Kotlin + Gradle (Kotlin DSL)** — single app module, no Android Studio project files needed to build/run.
- **Two direct, independent SAF pickers — no vault root, no guessing.** "Choose daily folder" (`ACTION_OPEN_DOCUMENT_TREE`, `VaultPrefs.treeUri`) points straight at the daily-notes folder itself (e.g. `02 - daily`); "Choose daily template" (`ACTION_OPEN_DOCUMENT`, `VaultPrefs.templateUri`) points straight at the template file. Both persisted via `takePersistableUriPermission`. `DailyNote` treats `treeUri` as literally the daily folder — no subfolder/sibling search, since SAF can't walk up to a parent anyway. "Create today's note" copies the picked template if set, else starts blank.
- **Settings are a separate screen, not inline above the editor.** `MainActivity`'s `Scaffold`/`TopAppBar` toggles between `SettingsScreen` (the two pickers) and `EditorScreen` (note preview/edit) via a `showSettings` bool — a `⚙` action opens settings, `Done` closes it. Lands on settings first run (no daily folder picked yet); everyday use opens straight to the editor. The top bar title shows the open file's name (not a static "DailyObsi" label) once a note is loaded, and `Back to today`/`Edit`↔`Read` live in the top bar actions (left-to-right in that order) rather than a row above the note, so the note body gets the vertical space back.
- **The markdown code is split across three files by concern, not one 1000+-line `Markdown.kt`:** `MarkdownParsing.kt` (shared regexes/`Block`/`parseBlocks`/`headerBodyLineRange`/colors — no Compose UI, imported by both of the below), `MarkdownReading.kt` (the LazyColumn-based reading-mode renderer: `MarkdownView`/`MarkdownLine`/`EmbedImage`/`CodeBlock`/`ProgressBarBlock`), and `MarkdownEditing.kt` (the `TextFieldState`-based raw-markdown editor: `MarkdownTextField`/`highlightMarkdownForEdit`/the input & output transformations). Things previously `private` in the single file were widened to default (public) visibility only where a different file now needs them — everything still file-scoped where it was before stays `private`. References below to "`Markdown.kt`" from before the split mean whichever of these three actually holds that symbol now.
- **Reading mode is the default, edit mode is opt-in.** `EditorScreen` renders `MarkdownView` (`MarkdownReading.kt`) unless `editMode` is toggled via the top bar's `Edit`/`Read` action. `loadNote()` always resets `editMode = false`, so opening a note (today, or "yesterday" below) starts in reading mode.
- **`MarkdownTextField` (`MarkdownEditing.kt`) is the shared raw-markdown editor for both main edit mode and the section editor, built on the newer `TextFieldState`-based `BasicTextField`** (`androidx.compose.foundation.text.input`, stable since Compose Foundation 1.8.0 — `app/build.gradle.kts` bumped `compose-bom` from `2024.12.01` to `2025.09.00` specifically for this), not the classic `(String, (String)->Unit)`/`TextFieldValue` overload used everywhere else historically. Two things that classic API genuinely can't do drove the switch:
  - **Checkbox lines render a real overlaid `Checkbox`, pixel-matched to reading mode**, not a styled-text lookalike. `markdownOutputTransformation` hides (transparent, not deleted — still reserves layout space) each checkbox line's `"- [ ]"`/`"- [x]"` span via `OutputTransformation.addStyle`, then `MarkdownTextField` overlays a real `Checkbox(onCheckedChange = null)` — non-interactive by design, since "in edit mode I just want to write" was explicit; tapping it does nothing rather than fighting cursor placement — positioned with `TextLayoutResult.getBoundingBox` at `CheckboxOverlaySpec.anchorOffset` (the hidden span's start, *after* leading indentation, matching reading mode's checkbox position after the indent padding). When `onShiftIndent`/`onMoveLine` are supplied (main edit mode only — see below), the same overlay also gets the swipe gesture (`detectSwipeToIndent`, shared with reading mode's checkbox row) and `▲`/`▼` reorder icons pinned to the field's right edge, matching reading mode there too.
  - **The overlay stays correctly positioned while scrolling** via a `ScrollState` hoisted in `MarkdownTextField` and passed to *both* `BasicTextField`'s own `scrollState` param and the overlay's `Modifier.offset` math (`... - scrollState.value`) — the classic API never exposed its internal scroll offset, which is what made this actually infeasible there; researched via the `Hyphen` Compose Multiplatform markdown editor's real source (`ui/checkbox/InlineCheckbox.kt`, `ui/internal/InlineContentHost.kt`) to confirm this exact shared-`ScrollState` pattern before building it. This still means one continuous text field (free typing, normal Enter/Backspace/multi-line select) rather than per-line fields — the alternative (segmenting edit mode into per-line composables so reading mode's row could be reused wholesale) was considered and explicitly rejected in favor of this, to preserve continuous typing.
  - **`onShiftIndent`/`onMoveLine` are optional params — `MarkdownTextField` always reports line indices local to whatever `value` it was given, not the file.** Main edit mode's `value` *is* the full file, so its callbacks operate on `text` directly. The section editor's `value` is the extracted draft, so its callbacks operate on `sectionDraft` via the same `onDraftChanged` the text editing already uses — *not* on the file directly, which would go stale against the still-open draft until Save overwrites it.
  - **No floating "insert checkbox" button, no per-row ⇤⇥▲▼ buttons, no swipe gesture** — all three were tried and ripped back out, in that order. The FAB (bottom-right, above the keyboard) sat right where a thumb naturally rests while typing, so normal typing kept accidentally re-triggering it *between keystrokes*, visibly shredding whatever word was being typed into a run of single-character checkbox lines. Its replacement, per-row ⇤⇥▲▼ buttons pinned to each checkbox row's right edge, and before that a full-row swipe zone, both had the same underlying problem from a different angle: any hit-target positioned on top of the row ate taps meant to place a cursor in the todo text right next to it -- unlike reading mode's row (plain static `Text`, nothing underneath to conflict with), this row's text *is* the real editable field. None of these threw an exception -- all placement/hit-testing bugs, not logic bugs.
  - **What's there instead: a single floating bubble, not tied to any row's position, acting on whichever line the cursor currently sits on.** One small `Surface` (bottom-end, `Modifier.imePadding()`, deliberately compact — 18dp icons in 32dp touch targets, `LocalMinimumInteractiveComponentSize provides 0.dp`, not full 48dp Material defaults, so it reads as a minor utility rather than a dominant FAB) holds all four ⇤⇥▲▼ `IconButton`s. `cursorLineIndex` is derived by counting `\n` before `state.selection.start` in `state.text`, recomputed via `remember(state.text, state.selection)`. Since there's exactly one bubble at a fixed screen position instead of one overlay per checkbox line scattered through the document, there's nothing left sitting on top of the text to steal cursor-placement taps.
  - **Bug fixed: every bubble tap used to snap the view to the very end of the document.** `MarkdownTextField`'s resync effect (below) originally called `setTextAndPlaceCursorAtEnd(value)` unconditionally whenever `value` changed for a reason other than the field's own typing — but *every* ⇤⇥▲▼ tap changes `value` exactly that way (`onShiftIndent`/`onMoveLine` call `persist()` in `DailyObsiApp` directly, bypassing `onValueChange` entirely), so each tap slammed the cursor to the document's end and the view followed it there. Fixed by preserving the prior cursor *offset* (`state.selection.start.coerceIn(0, value.length)`) across the resync instead of always jumping to the end. `Log.d("DailyObsiEdit", ...)` calls sit on this resync path and on each bubble button's `onClick` specifically so this class of bug is checkable via logcat next time, not just re-diagnosed by reading code.
  - **Checkbox lines auto-continue on Enter too, via the same `listContinuationInputTransformation`** ordered lists use (renamed from `orderedListInputTransformation`) — pressing Enter at the end of `"- [ ] text"`/`"- [x] text"` inserts a fresh *unchecked* `"- [ ] "` on the new line regardless of whether the split-off item was checked; Enter on an empty item strips the marker instead (exits the list), same rule as ordered lists. This is what actually creates new checkbox lines now -- not a button.
  - **Ordered-list auto-continue on Enter is an `InputTransformation`**, not a hand-diffed `TextFieldValue` comparison: `changes.getRange(0)`/`getOriginalRange(0)` directly identify "exactly one `\n` inserted, nothing replaced" without manual substring diffing. Pressing Enter at the end of a `"1. text"` line inserts `"2. "` on the new line (incrementing per existing item); Enter on an *empty* `"N. "` item strips the marker instead of continuing forever (Obsidian/Notion-style list-exit).
  - **All markdown styling (bold/italic/highlights/headers/etc.) is preserved by replaying `highlightMarkdownForEdit`'s existing `AnnotatedString.spanStyles` onto the `OutputTransformation`'s `TextFieldBuffer` via `addStyle`** — that function itself didn't need to change (it's still length-preserving, so its offsets stay 1:1 valid), only the wrapper around it did.
  - `value`/`onValueChange` stay a plain `String` API for both call sites — `MarkdownTextField` manages a `TextFieldState` internally, resyncing via `LaunchedEffect(value)` (cursor-offset-preserving `state.edit { replace(...); placeCursorBeforeCharAt(...) }`, see the bubble bug above — not `setTextAndPlaceCursorAtEnd`, that was the bug) whenever `value` changes for a reason other than its own edit; its own edits round-trip back to an equal `value` via `snapshotFlow { state.text.toString() }`, so the resync never fights mid-keystroke.
- **Edit mode's font size matches reading mode.** The field's base `textStyle` was bumped from `bodyMedium` (14sp, "way too small") to `bodyLarge` (16sp, reading mode's size) with `fontSize` dialed back slightly to 15sp since edit mode also carries visible raw syntax.
- **Edit mode is a borderless, fullscreen `BasicTextField` with no Save button.** No `OutlinedTextField` box/frame, no padding around it (`EditorScreen` zeroes the outer `Column`'s padding specifically when `editMode`) — the raw markdown gets the whole screen. There's no Save action at all: `DailyObsiApp` autosaves on a 10s `LaunchedEffect(editMode)` tick while editing, on `ON_STOP` (`LifecycleEventObserver`, e.g. backgrounding/killing the app mid-edit), and immediately whenever edit mode is exited — via the top bar's `Edit`/`Read` toggle *or* the system back button, both routed through one `exitEditMode()` that persists then flips `editMode = false`. Back is intercepted with `BackHandler(enabled = editMode)` so it exits to reading mode instead of leaving the screen/app while editing.
- **The renderer is pragmatic, not full CommonMark** — scoped to exactly what `00 - todo/daily template.md` actually uses: `#`/`##`/... headers (vs. Obsidian `#tag` lines, which need the space-after-# distinction to tell apart; headers are collapsible in reading mode, see below), bold/italic/strikethrough/inline code, `==highlights==` and `<mark class="hltr-flashy-*">` HTML highlights (Highlightr plugin — color guessed from the class name), `[[wikilinks|alias]]` (styled only, not navigable — the rest of the vault isn't in the SAF grant), `![[embeds]]` (resolved to a real image via Coil + `DailyNote.findAttachment`'s bounded-depth SAF search when findable — usually *isn't*, since attachments live next to the vault root, outside the picked daily folder; falls back to a "not found" placeholder rather than failing silently), ordered/unordered/checkbox lists with indentation, blockquotes, horizontal rules, and fenced ` ```progressbar ` blocks. Progress-bar blocks with `kind: manual` + `button: true` (the medication/task counters) get real `−`/`+` controls that rewrite the block's `value:` line in place; `day-year`/`day-custom` kinds compute progress from dates instead and aren't interactive. Every interaction in reading mode (checkbox toggle, indent shift, reorder, progress +/-) routes through the same `persist()` in `DailyObsiApp` — writes the file and calls `TodoWidget().updateAll()`, so nothing needs an explicit save.
- **Checkbox rows: `▲`/`▼` (Material `KeyboardArrowUp`/`Down` icons) reorder the line, a horizontal swipe indents/outdents it.** `DailyNote.moveLine` swaps a line with its immediate neighbor for reordering tasks vertically, disabled at the file's first/last line. Indent/outdent (`DailyNote.shiftIndent`) moved off dedicated buttons onto a swipe gesture on the row itself, firing `onShiftIndent` once past a ~56dp threshold on release, not continuously per pixel. The gesture is hand-rolled (`awaitEachGesture`/`awaitFirstDown`, not `detectHorizontalDragGestures`) specifically to coexist with the enclosing `LazyColumn`'s vertical scroll: plain horizontal-only drag detection has no concept of "this gesture is actually a scroll" and steals any touch the moment its horizontal component crosses touch-slop, even on a mostly-vertical swipe. The fix waits for slop on *either* axis, then only locks into swipe handling (and starts calling `change.consume()`) if the horizontal delta clearly dominates the vertical one (1.5x); otherwise it bails without consuming so the list scroll gets the gesture instead.
- **Headers are color-coded by level** (`headerColorFor` in `MarkdownParsing.kt`, used by both `MarkdownReading.kt` and `MarkdownEditing.kt`): h2 pink, h3 flamingo, h4 rosewater, h6 blue, h1/h5 left at the default text color — matching leftover AnuPpuccin `style-settings` config found in the vault (`.obsidian/plugins/obsidian-style-settings/data.json`), even though the *currently active* theme (`Velocity Custom`) doesn't itself use distinct header hues (its `--h1-color`..`--h6-color` are just low-saturation lightness steps of one base tone). Colors are the Catppuccin *Latte* hex values specifically, not Mocha — Mocha's pastels are too washed out against a light background and this app doesn't split header color by light/dark theme.
- **`EmbedImage` (`MarkdownReading.kt`) caches resolved `![[embed]]` URIs process-wide** (`attachmentUriCache` in `MarkdownParsing.kt`, keyed on `"dailyUri|name"`) — without it, every time a `LazyColumn` item holding an embed scrolled out of the viewport and back in, Compose disposed and recomposed it from scratch, re-running the bounded-depth SAF `findAttachment` DFS and re-fetching the image on every re-entry (visible as a "reload" flash). The cache survives across recompositions/scrolls for the life of the process; a stale-attachment edge case (a note's image swapped out on disk without an app restart) isn't handled, consistent with this app's existing bias toward simplicity here.
- **Headers are collapsible in reading mode, no fold-arrow indicator.** Tapping the header text itself toggles a per-line `collapsedHeaders: SnapshotStateMap<Int, Boolean>` in `MarkdownView`, keyed on `viewingDate` (not `text`) so a checkbox toggle/indent/reorder elsewhere doesn't reset fold state — none of those change line count/order for existing headers. `MarkdownView` filters `blocks` down to `visibleBlocks` each recomposition: collapsing a header hides every block after it up to (not including) the next header whose level is `<=` its own, i.e. a sibling or ancestor closing the section; deeper headers inside a collapsed section stay hidden regardless of their own fold state.
- **Edit mode gets the same visual styling as reading mode, not a second renderer, via `highlightMarkdownForEdit` (length-preserving, unlike reading mode's `appendMarkdownInline` which *hides* delimiters like `**`).** Its output is consumed by `markdownOutputTransformation` (see `MarkdownTextField` above) rather than the classic `VisualTransformation` this used before switching APIs. Progress-bar `+`/`-` still can't exist inline in edit mode's raw text (only checkboxes get a real overlaid widget, via the mechanism above) — that's what reading mode is for.
- **Missing today's note → offers yesterday, not just "create".** If there's no file for today, `EditorScreen` checks whether yesterday's note exists (`DailyNote.findFile(..., date.minusDays(1))`) and if so offers both "Open yesterday's note" and "Create today's note" side by side, rather than forcing straight into a blank note. Viewing a non-today date shows a "Back to today" action in the top bar.
- **Launcher icon supports Android 13+ themed (monochrome) icons.** `mipmap-anydpi-v26/ic_launcher*.xml` add a `<monochrome>` layer pointing at the same flat white shape already used for `ic_launcher_foreground` (no separate asset needed since it has no baked-in color) — the system recolors it to match the wallpaper/Material You palette when the user has "Themed icons" on, on launchers that support it (stock Pixel does).
- **Jetpack Glance** (`androidx.glance`) — the home-screen widget. Extracts today's checkbox lines with a plain regex on `- [ ]` / `- [x]` (no markdown parser needed for this). Tapping a line toggles the checkbox in place in the underlying file. A manual "↻" refresh tap forces a re-read since `provideGlance` always reads the file fresh — closes the gap between Termux's `git pull` and the OS's own ~30min widget refresh tick (there's no true push/FileObserver refresh; SAF-backed shared-storage URIs don't reliably support that).
- **Jetpack Compose** — the in-app screen: a full-file multiline text editor over the daily note's raw markdown; save writes straight back to the same file via `DocumentFile`. `MainActivity.onCreate` calls `enableEdgeToEdge()` *and* wraps content in `Surface(Modifier.fillMaxSize())` → inner `Box(Modifier.safeDrawingPadding())` — the padding goes on the *inner* Box, not the Surface itself. Padding the Surface directly shrinks its own bounds inward by the inset, so its background color never reaches behind the status/nav bars at all, leaving a visible mismatched-color gap/seam right at the screen edge (most noticeable as a "border" above the gesture-nav pill); with the inner Box instead, the Surface's background fills the literal full screen and only the content is pushed clear of the system bars. `res/values/themes.xml` + `res/values-night/themes.xml` split on `Theme.DeviceDefault(.Light).NoActionBar` for the window base (there's no framework "DayNight" style without AppCompat/Material Components, so the resource-qualifier split *is* the day/night switch). Theme color uses Material You dynamic color (`dynamicLightColorScheme`/`dynamicDarkColorScheme`) on API 31+, falling back to stock Material3 below that — confirmed against `../grid9`'s identical pattern. Note: dynamic color reflects the system's actual `theme_customization_overlay_packages` color source (e.g. `home_wallpaper`) — if that's wallpaper-derived rather than a manually-picked swatch, the app will correctly render whatever the wallpaper extracts to, not necessarily whatever's shown in a Settings color picker.
- **Embedded images get rounded corners** (`Modifier.clip(RoundedCornerShape(12.dp))` in `EmbedImage`).
- **Section editor: a pencil icon next to each header opens a separate page to edit just that header's body**, not the header text and not the whole note. `headerBodyLineRange(text, headerLineIndex)` (`MarkdownParsing.kt`) computes the inclusive raw-line range of the body — same boundary rule as the collapse feature (up to, not including, the next header whose level is `<=` this one), walking `parseBlocks` rather than raw lines so a `#` inside a fenced code block is never mistaken for a heading. `DailyObsiApp.openSectionEditor` extracts that range into `sectionDraft` and sets `editingSectionLine`, which is a third top-level screen state alongside `showSettings`/the editor (checked first in both the `TopAppBar` and the `Scaffold` content `when`/`if` chain) — its own `SectionEditorScreen` is the same borderless fullscreen `MarkdownTextField` as main edit mode, scoped to the draft string, *with* `onShiftIndent`/`onMoveLine` wired too — but operating on `sectionDraft` via `onDraftChanged`, not on the file directly (see `MarkdownTextField`'s doc comment for why: its line indices are always local to whatever `value` it's given, and the file won't reflect the draft until Save). Save (`DailyNote.replaceLines`) or Cancel both close it back to the reading page; system back while it's open is wired to Cancel via `BackHandler(enabled = editingSectionLine != null)`. No autosave here (unlike main edit mode) since leaving the page always resolves one way or the other via the top bar actions.

The git-pulled file in shared storage is the single source of truth; widget and editor both read/write it directly, no intermediate state.

## Local dev environment (this machine)

The Android SDK is split across two roots — both are needed, for different things:

- `/opt/android-sdk` — the default `$ANDROID_HOME`/`$ANDROID_SDK_ROOT`, has `cmdline-tools`, `sdkmanager`, `avdmanager`, `platform-tools/adb`. Use this for building (`./gradlew`) and `adb`. It does **not** have the emulator system image.
- `/home/ayaya/Android/Sdk-avd` — has the `emulator` binary and the actual system image (`system-images/android-35/google_apis/x86_64`). To launch the emulator, point env vars here instead:
  ```
  ANDROID_SDK_ROOT=/home/ayaya/Android/Sdk-avd \
  ANDROID_HOME=/home/ayaya/Android/Sdk-avd \
  ANDROID_AVD_HOME=/home/ayaya/.config/.android/avd \
  /home/ayaya/Android/Sdk-avd/emulator/emulator -avd <name>
  ```
  (`ANDROID_AVD_HOME` is required — the AVD configs live in `~/.config/.android/avd`, not the default `~/.android/avd`.)

Configured AVDs: `grid9test`, `recoral_test` (both android-35 google_apis x86_64).

`app/build.gradle.kts` pins `buildToolsVersion = "37.0.0"` deliberately — that's what's actually installed under `/opt/android-sdk/build-tools/`. AGP's default (34.0.0) isn't installed and there's no `licenses/` dir to auto-accept it from, so leaving it unpinned fails the build on a license-not-accepted error.

**`./run.sh`** does the whole cycle in one shot: boots `grid9test` if no device is attached (skips straight to build if one already is), `assembleDebug`, `adb install -r`, force-stop + relaunch. Use this instead of re-deriving the env-var dance above by hand.

## Signing

`release-keystore.jks` (PKCS12, alias `dailyobsi`, self-signed, 10000-day validity) + `keystore.properties` hold the release signing key. Both are gitignored — never commit them. `app/build.gradle.kts` reads `keystore.properties` at config time and wires a `release` `signingConfig` only if the file exists, so a checkout without it still builds (just unsigned/debug-signed release). PKCS12 keystores don't support distinct store/key passwords — `keytool` silently reuses the store password for the key, so `keystore.properties`' `storePassword` and `keyPassword` are intentionally identical.

## Testing

Installed and running on the `grid9test` AVD: a full copy of `~/obsidian/main` was `adb push`ed to `/sdcard/obsidian` on the emulator (not a symlink/sync -- a one-time snapshot copy, so it goes stale; re-push if the on-device vault needs to reflect later edits made on the dev machine), and `dev.ayaya.dailyobsi` is installed via `adb install -r`. When picking a folder in the app on this AVD, point it at `obsidian/main` under Internal storage.

**Check logcat after every install/launch, not just when something visibly breaks.** `adb logcat -c` right before `./run.sh` (or right after), then `adb logcat -d | grep -iE "dailyobsi.*(fatal|exception|error)"` once the app's up — a clean run should show nothing. Silent logic bugs (bad state, wrong output) won't throw, so this only catches crashes/exceptions, but it's a cheap check worth doing every time regardless, not just when chasing a specific crash.
